# Фаза 1: Интеграция Stealth Addresses (Детальный План для Новой Сети)

## Введение

Поскольку сеть запускается с нуля (нет легаси-кошельков), мы можем оптимизировать архитектуру, не оглядываясь на старые форматы адресов (P2PKH/P2SH). Мы сделаем Stealth Addresses **единственным стандартом** для пользовательских переводов.

### Стратегия Квантовой Безопасности (Quantum Resistance Strategy)

Мы применяем гибридный подход "Безопасность через Одноразовость и Скорость" (Security via Ephemeral Keys & Speed), чтобы обеспечить защиту средств без ущерба для производительности сети.

#### 1. Почему мы отказываемся от тотальных PQ-подписей (ML-DSA)
Использование пост-квантовых подписей (Dilithium/ML-DSA) для каждой транзакции увеличивает размер данных с ~300 байт до ~3-5 КБ. Для высокоскоростного DAG (10+ блоков в секунду) это создаст колоссальную нагрузку на сеть и хранилище, делая децентрализацию невозможной (ноды не смогут синхронизироваться).

#### 2. Наше решение: Ephemeral Keys (Временные Ключи)
Вместо "тяжелой брони" мы используем тактику "невидимки":

*   **Состояние Покоя (Data at Rest):**
    *   Пользовательские средства хранятся на **Стелс-адресах** (одноразовых ключах).
    *   Публичный ключ получателя (`P_dest`) математически вычисляется, но **никогда не публикуется** в открытом виде в блокчейне до момента траты.
    *   В блокчейне виден только эфемерный ключ отправителя (`R`), который бесполезен для взлома средств.
    *   **Результат:** Квантовый компьютер не может взломать ключ, которого он не видит. Средства в безопасности неограниченно долго.

*   **Состояние Движения (Data in Motion):**
    *   Публичный ключ раскрывается **только в момент подписания транзакции** на трату.
    *   С этого момента начинается "гонка": транзакция летит в мемпул -> попадает в блок -> финализируется.
    *   В нашей быстрой DAG-сети это окно уязвимости составляет **секунды**.
    *   Для взлома ключа (алгоритм Шора) даже мощному квантовому компьютеру требуются минуты или часы.
    *   **Результат:** Транзакция подтверждается быстрее, чем хакер успевает вычислить приватный ключ.

#### 3. Роль ML-DSA (Dilithium)
Тяжелая пост-квантовая криптография (ML-DSA) сохраняется в протоколе, но используется избирательно:
*   Для подписи критических обновлений сети (Checkpointing).
*   В будущем (Фаза 2): Для "Холодных Хранилищ" (Cold Storage Accounts), где средства лежат годами и не двигаются часто.

## 1. Криптографическое Ядро (`crypto/`)

Эта часть — фундамент. Здесь любая ошибка = потеря средств навсегда.

### 1.1. Реализация примитивов Diffie-Hellman

**Файл:** Создать новый модуль `crypto/src/stealth.rs`.
**Задача:** Реализовать математику `secp256k1` для создания общего секрета.

**Детальная логика:**

1.  **Генерация ключей:**
    -   Пользователь имеет два ключа: `ScanKey` (для поиска входящих) и `SpendKey` (для траты).
    -   Публичный адрес теперь — это пара `(PubScan, PubSpend)`.

2.  **Отправка (Sender):**
    -   Генерация одноразового секрета `r` (random scalar).
    -   Вычисление `R = r * G` (Ephemeral Public Key) — это мы положим в блокчейн открыто.
    -   Вычисление общего секрета `S = r * PubScan` (ECDH).
    -   Вычисление "ослепляющего фактора" `t = Hash(S)`.
    -   Вычисление адреса назначения `P_dest = PubSpend + t*G`.

3.  **Получение (Receiver):**
    -   Видит в блокчейне `R`.
    -   Вычисляет `S = PrivScan * R`. (Магия ECDH: `r * PubScan == PrivScan * R`).
    -   Вычисляет `t = Hash(S)`.
    -   Проверяет: "Соответствует ли этот выход моему адресу?" -> `P_blockchain == PubSpend + t*G`.
    -   Если да, вычисляет приватный ключ для траты: `PrivDest = PrivSpend + t`.

**Подводные камни и Оптимизация (Refinement):**

-   **Генератор случайных чисел (RNG):** Использовать *только* `OsRng`. Если `r` будет предсказуемым, хакер восстановит приватный ключ получателя.
-   **Hash Function:** Используем Blake2b или SHA3. Важно использовать *domain separation* (уникальные префиксы для хеширования), чтобы `Hash(S)` для генерации ключа не совпал с чем-то еще.
-   **Проверка точки на кривой:** При парсинге `R` из блокчейна нужно строго проверять, что точка лежит на кривой (is_on_curve), чтобы избежать атак с подменой группы (Small subgroup attacks).

### 1.2. View Tags (Оптимизация для мобилок)

**Задача:** Ускорить фильтрацию транзакций в 100+ раз.
**Реализация:**

-   Взять первый байт от хеша секрета: `Tag = Hash("view_tag", S)[0]`.
-   При сканировании: сначала проверяем байт. Если не совпал — пропускаем (экономим 2 тяжелые операции умножения на кривой).

### 1.3. Формат Адреса (UX)

**Задача:** Визуально отделить стелс-адреса от системных или легаси.
**Решение:**
-   Использовать **Bech32m**.
-   **HRP (Human Readable Part):** `qs` (Qaspa Stealth).
-   **Пример:** `qs1...`
-   **Payload:** Сериализованные `(PubScan, PubSpend)`.

## 2. Консенсус и Формат Транзакции (`consensus/core/`)

Так как мы не поддерживаем легаси, мы можем сделать формат "чище".

### 2.1. Новый формат ScriptPublicKey (Native Stealth)

**Файл:** `consensus/core/src/tx/script_public_key.rs`
**Изменения:**
Вместо использования хака с `OP_DROP` (который нужен для совместимости с P2PKH), мы вводим **Новую Версию ScriptPublicKey**.

-   **Версия:** `ScriptPublicKeyVersion::Stealth (v1)` (или v2, если 0/1 заняты).
-   **Структура (Raw Bytes):** `[33 bytes: Ephemeral PubKey R] [1 byte: View Tag] [32 bytes: Stealth PubKey P (XOnly)]`
-   **Размер:** 66 байт. (Это компактнее, чем 80 байт с опкодами).
-   **Логика выполнения (VM):**
    -   **Интеграция с VM:** Мы не добавляем новые опкоды.
    -   Если версия скрипта `Stealth`, VM **не запускает** стек опкодов.
    -   Вместо этого вызывается нативная функция валидации (`Native SegWit` подход), которая проверяет Schnorr-подпись для ключа `P` из witness-данных.

**Критические моменты:**

-   **Сериализация:** Убедиться, что новый формат корректно сериализуется в Borsh и JSON.
-   **Pruning:** Эти данные остаются в UTXO сете.

## 3. Кошелек и Управление Ключами (`wallet/core/`)

Самая объемная часть работы. Кошелек должен "поумнеть".

### 3.1. Новая структура аккаунта и Derivation

**Файл:** `wallet/core/src/storage/account.rs`
**Изменения:**

-   **Стандарт:** Строго **BIP-39** (12/24 слова). Не используем кастомные форматы сидов.
-   **Derivation Path:** Используем разные ветки BIP-32 для Scan и Spend ключей, чтобы сохранить совместимость и чистоту:
    -   **Spend Key (Трата):** `m/44'/111111'/0'/0'/0` (Account 0, External Chain).
    -   **Scan Key (Просмотр):** `m/44'/111111'/0'/1'/0` (Account 0, Internal/Scan Chain).
-   Основной тип аккаунта: `StealthAccount`.

### 3.2. Логика отправки (Transaction Generator)

**Файл:** `wallet/core/src/tx/generator/payment.rs`
**Алгоритм:**

1.  Пользователь вводит адрес `qs1...`.
2.  Парсер декодирует Bech32m в `(PubScan, PubSpend)`.
3.  Генератор для *каждого* выхода в транзакции создает *уникальный* `R` и `Tag`.
4.  Формирует `ScriptPublicKey` новой версии.
5.  **Комиссии (Fees):** В Фазе 1 разрешается оплачивать комиссию обычными UTXO (если они есть). Это может раскрыть отправителя, но получатель остается анонимным.

### 3.3. Логика сканирования (Scanner) — Оптимизация RPC

**Файл:** `wallet/core/src/utxo/scan.rs` и `rpc/`
**Проблема:** Сканирование с нуля по BIP-39 долгое.
**Решение:** Реализовать метод RPC `get_block_view_tags`.

**Алгоритм:**
1.  **Индексация:** Ноде не нужен отдельный сложный индекс. Она читает блоки с диска, извлекает байт View Tag из ScriptPublicKey и отдает клиенту.
2.  **Light Client Mode:** Кошелек запрашивает у ноды стрим View Tags.
3.  **Локальная фильтрация:**
    -   Кошелек быстро (в памяти) проверяет: `Hash(SharedSecret)[0] == Tag`.
4.  **Загрузка блоков:**
    -   Только если найден "Кандидат", кошелек скачивает полный блок.
5.  **Сохранение:**
    -   Найденные UTXO сохраняются в локальную БД.
    -   **CRITICAL:** Сохраняем `OneTimePrivKey` (вычисленный приватный ключ для траты) в зашифрованном виде.

**Обработка Реорганизаций (Reorgs):**
-   Кошелек слушает события `ChainChanged` (Added/Removed blocks).
-   При событии `Removed(BlockXYZ)` кошелек находит все UTXO из этого блока в своей БД и удаляет их (вместе с вычисленными Ephemeral Keys), чтобы избежать траты несуществующих монет.

## 4. План Тестирования (QA)

### 4.1. Property-Based Tests (Fuzzing)

Сгенерировать сценарии с помощью ИИ (`proptest`):

1.  **Sender-Receiver Match:** Сгенерировать 1000 пар ключей и транзакций. Убедиться, что получатель *всегда* может восстановить ключ.
2.  **Privacy Check:** Убедиться, что из `P_dest` и `R` *невозможно* математически получить `PubSpend` получателя (необратимость).
3.  **Tag Collision:** Проверить, что будет, если Tag случайно совпал (коллизия 1/256). Кошелек должен провести полную проверку и корректно отвергнуть чужую транзакцию, а не добавить её себе как "нетратимую".
4.  **Invalid Curve Points:** Скормить парсеру "мусорные" байты вместо R. Проверить, что нода не падает (panic), а возвращает ошибку.

### 4.2. Integration Test

1.  Поднять локальный devnet (с новым генезисом).
2.  Майнить блоки на стелс-адрес `qs1...`.
3.  Отправить со стелс-адреса на другой стелс-адрес.
4.  Восстановить кошелек из Seed (без указания даты) и проверить, что баланс подтянулся через механизм View Tags.
5.  Проверить, что в эксплорере адреса выглядят как случайный шум.


Вот мои ответы и уточнения к плану:

### 1. Derivation Path для Stealth Keys
**Вопрос:** Как деривировать Scan и Spend ключи из одного Seed?
**Решение (как в Monero/Silent Payments):**
Мы используем разные ветки (Change/Purpose level) в BIP-32 дереве.

*   **Spend Key (Секретный ключ траты):** `m/44'/111111'/0'/0'/0` (Стандартный Account 0).
    *   Это "Главный ключ", который контролирует деньги.
*   **Scan Key (Ключ сканирования):** `m/44'/111111'/0'/1'/0` (Ветка 1).
    *   Или деривируем его хешированием Spend Key (как в Monero), но BIP-32 чище и понятнее для аппаратных кошельков.
*   **Важно:** Для каждого нового "Аккаунта" (Account 1, 2...) просто инкрементируем индекс аккаунта: `m/44'/111111'/1'/...`.

### 2. Интеграция с VM (Script Engine)
**Вопрос:** Новый ScriptPublicKey (v1) без опкодов. Как VM поймет, что делать?
**Решение:**
Мы **не добавляем** новые опкоды. Мы меняем логику `pay_to_script_hash` или создаем новый тип шаблона `pay_to_stealth`.

*   Текущая VM (Kaspa) проверяет версию скрипта.
*   Если `Version == 0` (Legacy): запускает стандартный стек опкодов.
*   Если `Version == Stealth` (наша новая):
    *   VM **не запускает** стек опкодов вообще.
    *   VM сразу вызывает нативную функцию `check_schnorr_signature(pubkey=script[34..], sig=witness)`.
    *   Это называется "Native SegWit" подход (как P2WPKH в Биткоине) — это быстрее и дешевле по газу, чем парсить опкоды.

### 3. RPC `get_block_view_tags` и Индексация
**Вопрос:** Где хранить теги?
**Решение:**
Теги (View Tags) — это часть заголовка транзакции (или её UTXO).
*   Нам **не нужен** сложный отдельный индекс (как для адресов).
*   Теги хранятся внутри блоков.
*   RPC `get_block_view_tags` просто читает блок с диска, выдирает из каждой транзакции 1 байт тега и отдает массив байт.
*   **Оптимизация:** Можно хранить "Compact Block Filter" (BIP-158) отдельно, но для старта просто чтение блока с диска (SSD) достаточно быстрое, если мы не парсим весь блок, а только смещения.

### 4. Реорганизации (Reorgs)
**Вопрос:** Как чистить кеш ключей при реорге?
**Решение:**
Кошелек (Wallet Daemon) слушает события `ChainChanged` (добавленные и удаленные блоки).
*   Когда приходит событие `Removed(BlockXYZ)`:
    *   Кошелек находит все UTXO, созданные в `BlockXYZ`.
    *   Удаляет их из таблицы `utxos`.
    *   Удаляет связанные с ними приватные ключи из таблицы `ephemeral_keys` (если мы их кешировали).
*   Это стандартная логика работы любого SPV-кошелька, просто добавляется удаление ключей.
